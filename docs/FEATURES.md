# Features

Everything the Code Archaeologist needs, split into features. Each feature is a unit of work that fits in one branch and one pull request.

IDs have a prefix per area (e.g. `EXC-02`), so branches can be named `feature/EXC-02-rename-tracking`. IDs are stable: when a feature is split, add new IDs instead of renumbering.

## Rules for every feature

- **Nothing private shows up anywhere.** The agent's console output, audit log, reports, traces and commits never show local paths, user or machine names, e-mail addresses, secrets or credentials, and neither do the project's own files (code, tests, docs, this backlog). The conduct tests (FND-08) check this on every build: a feature that adds a command, an option or a new kind of output adds a scenario to them.
- **The user's credentials are off limits.** No feature reads, copies or mounts the home folder or its credential files and folders (`~/.m2`, `~/.gradle`, `~/.ssh`, `~/.aws`, `~/.docker`, `~/.config`, `~/.npmrc`, `~/.netrc`, `~/.git-credentials`, `~/.gitconfig`), and no container gets environment variables from the host. Only the copy of the repository under analysis and the agent's own caches go into a container.
- **The repository's code is not trusted.** Its build scripts, tests and Git hooks run only inside the sandbox, never on the user's machine.

## 1. Excavator: Git mining (EXC)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| EXC-01 | Git log reader | Runs `git log --numstat` over the last N years (read-only) and parses each commit: hash, author, date, message, lines added and removed per file, binary files included. Git runs with the commands a repository can define switched off (hooks, external diff, text conversion, fsmonitor) and without the user's global configuration | FND-03 |
| EXC-02 | Rename tracking | The history of renamed or moved files is credited to the file's current path | EXC-01 |
| EXC-03 | Bulk commit filter | Commits that touch more than N files (reformatting, license headers, mass moves) are left out of churn, but their renames are still tracked | EXC-02 |
| EXC-04 | Bug-fix classifier | Detects fix commits from the message with English and Portuguese keywords (`fix`, `bug`, `hotfix`, `corrige`, `erro`...) and issue-key patterns | EXC-01 |
| EXC-05 | Per-file history | Aggregates per file: commits, changed lines, fix commits, distinct authors (respecting `.mailmap`), last change date. Authors are counted, never listed: their names and e-mail addresses stay out of reports and logs | EXC-02, EXC-03, EXC-04 |
| EXC-06 | Temporal coupling | Pairs of files that change together, with co-change count and confidence | EXC-05 |
| EXC-07 | LLM commit classification | Classifies commits with vague messages ("adjustments", "wip") as fix or not, using the local model | EXC-04, INF-04 |

## 2. Cartographer: code metrics (CAR)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| CAR-01 | Source scanner | Finds `.java` files, skips build, output and generated folders, and tells production code from test code | FND-03 |
| CAR-02 | Legacy encoding support | Reads sources as UTF-8 and falls back to Cp1252/ISO-8859-1, so old files with accented characters parse correctly | CAR-01 |
| CAR-03 | Tolerant Java parsing | Parses Java 1.4 to 21 with JavaParser, trying the oldest language level first; files that fail are listed in the report instead of stopping the run | CAR-02 |
| CAR-04 | Size metrics | Per class: lines of code (no comments or blank lines), number of methods, size of the largest method | CAR-03 |
| CAR-05 | Cyclomatic complexity | Complexity per method and per class (total and max); methods of anonymous classes are counted separately | CAR-03 |
| CAR-06 | Build and Java version detection | Detects the build system (Maven, Gradle, Ant) and the source/target Java version of each module | CAR-01 |
| CAR-07 | Dependency profile | Flags what makes a class hard to test: database (JDBC/JPA), file and network I/O, current time, randomness, static singletons, reflection, serialization | CAR-03 |

## 3. Prioritization (PRI)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| PRI-01 | Risk score | Normalizes each signal to 0..1 within the repository (log scale) and computes `churn × complexity × (1 + w_fixes × fixes + w_authors × authors)` with configurable weights | EXC-05, CAR-04, CAR-05 |
| PRI-02 | Hotspot report | `hotspots <repo>` writes a Markdown report (top N, with the evidence for each) and a CSV/JSON file with every class. Text from the repository is escaped in the Markdown, so it can't turn into links or remote images, and paths are relative to the repository | PRI-01, FND-02, FND-04 |
| PRI-03 | Weight calibration | Runs the report on the sample repository and on real open-source legacy projects, tunes the default weights and documents the results | PRI-02, FND-07 |
| PRI-04 | Feasibility score | Estimates how likely the agent is to succeed on a target: size versus model context, dependency profile, test difficulty | PRI-01, CAR-07 |
| PRI-05 | Target queue | Final queue ordered by risk × feasibility, with skip rules (generated code, interfaces, classes that are already modern) and a max-targets limit | PRI-04 |

## 4. Build sandbox (SBX)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| SBX-01 | Build runner | Runs the project's build and tests with the right commands for its build system (Maven, Gradle or Ant). Until SBX-02 is in place it is used by tests only: no command builds the user's project directly on their machine | CAR-06 |
| SBX-02 | Docker isolation | Runs builds and tests in containers with `--network none` (through Testcontainers), with images for old JDKs (6, 7, 8) and new ones (17, 21). The container runs as a non-root user, with CPU, memory, process and time limits and a read-only file system outside its work folder, and gets nothing from the host but the copy of the repository: no home folder, no credential folders, no host environment variables. A test lists the container's mounts and environment to prove it | SBX-01 |
| SBX-03 | Offline dependency cache | Downloads the project's dependencies once, with network, into an agent-owned cache, then mounts that cache read-only in the sandbox. The download runs in a container too (resolving dependencies runs build scripts such as `build.gradle`), with only the copy of the repository: never the user's `~/.m2` or `~/.gradle`, which may hold passwords. Private repositories need an explicit opt-in: a settings file the user points to, used only by the download container, never copied into the cache, the output or a log | SBX-02 |
| SBX-04 | Test result parser | Reads JUnit/Surefire XML reports: passed, failed and errored tests, with messages and stack traces to feed the fix loop | SBX-01 |
| SBX-05 | Coverage and mutation tools | Runs JaCoCo and PIT scoped to the target class and parses the coverage and mutation score | SBX-02, SBX-04 |

## 6. Guardian: characterization tests (GRD)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| GRD-01 | Test generation | Generates characterization tests for the target's public behavior (inputs, outputs, exceptions, side effects) with the LLM, using a test stack that runs on the project's JDK (JUnit 4 for Java 6/7, JUnit 5 for Java 8+) | INF-03, INF-04, INF-05, CAR-07 |
| GRD-02 | Non-determinism handling | Isolates time, randomness, database and collection ordering (mocks or seams) so the tests are deterministic | GRD-01 |
| GRD-03 | Baseline run | Runs the tests on the original code in the sandbox, repeats them to catch flaky tests, and asks the LLM to fix failures up to a limit; targets that can't get green tests are discarded | GRD-01, SBX-02, SBX-04 |
| GRD-04 | Test quality gate | Measures the coverage and mutation score of the generated tests and requires the configured minimum | GRD-03, SBX-05 |
| GRD-05 | Test integrity lock | Records the hash of each test file so later steps can prove the tests were not changed | GRD-03 |
| GRD-06 | Deterministic test generation spike | Evaluates Randoop/EvoSuite as a base the LLM improves on, compared with LLM-only generation | GRD-03 |

## 7. Workspace: Git branches (WRK)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| WRK-01 | Isolated working copy | Creates a separate `git worktree`, so the user's working copy and main branch are never touched | EXC-01 |
| WRK-02 | Branch management | Creates, stacks and deletes `archaeologist/*` branches; refuses any write to the main branch | WRK-01 |
| WRK-03 | Agent commits | Commits on agent branches with a structured message (target, refactoring, evidence). The repository's hooks are switched off (they are code from the repository), commits are authored by a fixed agent identity rather than the user's name and e-mail, and messages hold no local paths | WRK-02 |

## 8. Restorer: modernization (RST)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| RST-01 | Base migration branch | Applies the OpenRewrite `rewrite-migrate-java` recipes (8 → 11 → 17 → 21) to the whole repository, build files included, on `archaeologist/migrate-java21` | WRK-02, SBX-02 |
| RST-02 | JDK change check | Runs the characterization tests of the unchanged code on the new JDK, so JDK-related failures (e.g. `HashMap` ordering) are reported apart from refactoring failures | RST-01, GRD-03 |
| RST-03 | Refactoring catalog | Each modernization (Streams, switch expressions, pattern matching for `instanceof`, text blocks, `var`, records) is a type with its own applicability rules | CAR-03 |
| RST-04 | LLM refactoring | Applies one refactoring type to the target with the LLM, on its own branch stacked on the base branch | RST-03, INF-04, INF-05, WRK-02 |
| RST-05 | Self-correction loop | On a compile or test failure, sends the error back to the LLM and tries again, up to the limit | RST-04, SBX-04 |
| RST-06 | API preservation check | Compares public signatures before and after; API changes are only allowed in refactorings that update every caller | RST-04 |
| RST-07 | Pitfall guards | Blocks known-unsafe changes: records on JPA entities or setter-populated classes, Streams in hot loops, classes with reflection, serialization or custom `equals`/`hashCode` | RST-03, CAR-07 |

| ID | Feature | Delivers | Depends on |
|---|---|---|---|

## 12. Scout: hardware and model (SCT)

| ID | Feature | Delivers | Depends on |
|---|---|---|---|
| SCT-01 | Hardware detection | OS, CPU cores, AVX2, total and free RAM, GPU and VRAM (`nvidia-smi`, `rocm-smi`, Apple unified memory), free disk, on Linux, Windows and macOS | FND-03 |
| SCT-02 | Memory budget and model choice | Usable memory = available − system reserve − context reserve; picks the largest model in `models.yaml` that fits and classifies the machine as weak, medium or strong | SCT-01 |
| SCT-03 | Model download | Pulls the model through Ollama; supports air-gapped machines with pre-downloaded models | SCT-02, INF-01 |
| SCT-04 | Calibration | Measures tokens per second and runs a sample refactoring (`examples/RefactorLoop.java`) that must compile and pass; steps down one level on failure or slowness | SCT-03, SBX-02, INF-05 |
| SCT-05 | Machine profile | Saves the choice to `machine-profile.json` and redoes it when the hardware changes. The profile holds hardware figures only: no machine name, user name, serial number or path | SCT-04 |
| SCT-06 | Runtime downgrade | Steps the model down on its own when it runs out of memory, hangs or gets too slow, and keeps going | SCT-05, INF-06 |
| SCT-07 | Profile-based work mode | Adjusts scope per profile: one class with a short context (weak) up to whole packages (strong) | SCT-05, INF-03 |
| SCT-08 | Dual-model mode | Optional: a small model for simple tasks (classify commits, summarize) and the main one for tests and refactoring | SCT-05 |
